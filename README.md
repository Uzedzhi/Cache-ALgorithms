# cache_sim — симулятор многоуровневого кеша (LRU / LFU / ARC / 2Q / LIRS)

Небольшой исследовательский инструмент для сравнения алгоритмов вытеснения
кеша на произвольной многоуровневой иерархии, с эталонным сравнением против
идеального (беладиевского) кеша.

## Сборка

```
make
```

Собирается обычным `g++ -std=c++17`, без внешних зависимостей — только
стандартная библиотека (`std::variant` требует C++17). Заголовки ищутся в
`include/` и `MyCppLibs/` (см. `-Iinclude -IMyCppLibs` в `Makefile`).
`CMakeLists.txt` не нужен ввиду простоты проекта (4 .cpp + набор
header-only шаблонов).

## Запуск

```
./cache_sim [путь_к_конфигу]      # по умолчанию: config.txt
```

Данные подаются на **stdin**, конфигурация уровней читается из **файла**.

### Формат конфиг-файла

```
N
size_1 ALGO_1
size_2 ALGO_2
...
size_N ALGO_N
```

`ALGO` — одно из `LRU`, `LFU`, `ARC`, `2Q`, `LIRS` (регистр не важен).
Уровень 1 — самый верхний (ближе к "процессору"), уровень N — самый нижний.

Пример (`config.txt`):
```
2
4 LRU
2 LFU
```

### Формат входных данных (stdin)

```
M
d_1 d_2 ... d_M
```

Пример:
```
10
1 2 3 1 2 4 5 6 4 5
```

### Вывод

По строке на каждый уровень реальной иерархии, затем отдельной строкой —
эталон: один идеальный (беладиевский) кеш, которому отдан весь бюджет
памяти системы (сумма ёмкостей уровней).

```
Level 1 (LRU, capacity=4): 4 hits
Level 2 (LFU, capacity=2): 0 hits
Ideal (capacity=6): 4 hits
```

## Архитектура

### Общая база уровней — `TCacheLevelBase<Key, Entry>` (`include/CacheLevel.h`)

Наблюдение, ради которого она существует: чем бы ни отличались LRU, LFU,
ARC, 2Q, LIRS и идеальный кеш, устроены они одинаково — хеш-таблица
`ключ -> метаданные`, где запись бывает двух сортов:

- **резидентная** — ключ реально лежит в кеше, обращение к нему = хит;
- **призрачная** — ключ только помнится как история, данных за ним нет
  (списки `B1`/`B2` у ARC, `A1out` у 2Q, нерезидентный HIR у LIRS).
  Обращение к ней = промах, но алгоритм по этому факту подстраивается.

Значит, и `Contains()` у всех один и тот же: «запись нашлась **и** она
резидентная». Отличается только *как* запись отвечает на вопрос «я
резидентная?» — это единственное, что отдано наследникам: тип `Entry`
обязан иметь `bool IsResident() const`.

| алгоритм | тип записи    | `IsResident()`                     |
|----------|---------------|------------------------------------|
| LRU      | `SLruEntry`   | всегда `true` (призраков нет)      |
| LFU      | `SLfuEntry`   | всегда `true`                      |
| ARC      | `SArcEntry`   | `Location == T1 \|\| Location == T2` |
| 2Q       | `STwoQEntry`  | `Location == A1in \|\| Location == Am` |
| LIRS     | `SLirsEntry`  | флаг `Resident`                    |
| Ideal    | `SIdealEntry` | всегда `true`                      |

В базу уехало всё общее: сама хеш-таблица `Entries_`, ёмкость, тег
алгоритма, проверка «ёмкость больше нуля» и пустой хук
`NotifyStreamPosition()`. У наследников остаётся ровно одно — `Insert()`,
то есть сама политика вытеснения. Пять копий `Contains()`, пять копий
`GetCapacity()`/`GetAlgorithm()` и пять проверок ёмкости исчезли.

Наследование **невиртуальное**, vtable не создаётся: конкретный тип
уровня всегда известен статически. Деструктор базы `protected` — удалить
наследника через указатель на базу нельзя, и компилятор это подтвердит.

### Диспетчеризация — `std::variant` (`include/MultiLevelCache.h`)

`TCacheLevel<Key>` — это `std::variant` по всем шести классам. Уровни
лежат в `std::vector` по значению (без кучи), а вызов метода идёт через
`std::visit` с обобщённой лямбдой: раз все альтернативы наследуют одну
базу, у всех гарантированно есть нужный набор методов, и switch по
алгоритму разворачивает компилятор.

`MakeCacheLevel(Config, DataStream)` — обёртка-интерфейс: собрать уровень,
зная только его конфиг. Поток данных нужен исключительно идеальному кешу
(он заглядывает в будущее); остальные его игнорируют.

### `TCacheHierarchy<Key>` (`include/MultiLevelCache.h`)

«Структура с массивом кешей и методами». Принимает вектор
`SCacheLevelConfig` и сам поток, собирает уровни через `MakeCacheLevel` и
предоставляет ровно два действия:

- `CacheFind(key, position)` — проверяет наличие на каждом уровне сверху
  вниз (для статистики хитов), а затем **безусловно** поднимает ключ на
  уровень 0 через `CacheInsert`;
- `CacheInsert(levelIndex, key)` (приватный) — вставляет ключ на данный
  уровень; если это вызвало вытеснение, вытесненный ключ рекурсивно
  (каскадом) вставляется на `levelIndex + 1`.

Эта же пара функций без единого изменения обслуживает **и** реальную
иерархию из конфига, **и** эталонный прогон, где каждый уровень заменён
идеальным кешем — одна функция на оба прохода.

### `TIdealCache<Key>` (`include/IdealCache.h`)

Офлайн-оптимум Белади: на промахе вытесняет резидента, который
понадобится дальше всех в будущем (или не понадобится вовсе). Наследует
ту же базу, поэтому попадает в тот же `variant`. Единственное отличие —
непустой `NotifyStreamPosition()`, перекрывающий (сокрытием имени, не
через `virtual`) пустой хук базы. Жертва ищется через
`std::set<{следующее_использование, ключ}>` за O(log C).

### Чтение входа

- **`ConfigReader` / `InputReader`** — конфигурация из файла и данные из
  stdin. Проверка ошибок — через макросы `CHECK` / `CHECK_EX` из
  `MyCppLibs/sassert.h`, без `assert`. Фатальные ошибки (нет файла, битый
  конфиг, обрезанный поток) бросают; единственный
  `catch (const std::exception&)` — на верхнем уровне `main`, чтобы
  вывести внятное сообщение вместо аварийного завершения.
- **`SCacheLevelConfig`** (`include/CacheTypes.h`) — одна структура на весь
  проект: её отдаёт `ConfigReader` и её же принимает `TCacheHierarchy`,
  промежуточных копий-двойников нет.
- **`ParseCacheAlgorithm`** (`src/CacheTypes.cpp`) — разбор имени за
  **один проход**: символы приводятся к верхнему регистру и тут же
  копится хеш (FNV-1a), затем один `switch` по числу вместо цепочки
  сравнений строк. Приведённая строка нигде дальше не нужна, поэтому она
  и не создаётся — на вход берётся `std::string_view`, копии нет вообще.
  Нераспознанное имя **не бросает**, а возвращается как
  `ECacheAlgorithm::Unknown`; решение о фатальности принимает
  `ConfigReader` одним `CHECK_EX`.
- **`CacheAlgorithmToString`** — таблица `std::array<std::string_view, N>`,
  размер которой завязан на `ECacheAlgorithm::Unknown`: добавят алгоритм
  в enum и забудут имя — не соберётся.

## Допущения, зафиксированные в переписке

1. **Ёмкость идеального кеша** = сумма ёмкостей всех уровней реальной
   иерархии (общий бюджет памяти системы). Кеш именно **один** — почему
   не каскад из N идеальных уровней, см. следующий раздел.
2. **Каскадирование**: хит на любом уровне ⇒ ключ поднимается на уровень 0,
   вытесненные по пути элементы проталкиваются вниз; полный промах ⇒ ключ
   вставляется в уровень 0 и тоже может каскадом вытеснить что-то вниз.

## Почему эталон — один идеальный кеш, а не каскад из N

Соблазнительно повторить форму иерархии и заменить каждый уровень
идеальным кешем той же ёмкости — тогда видно по-уровневое сравнение. Но
**суммировать хиты такого каскада нельзя**: каждый уровень оптимизирует
только тот поток, который до него дошёл, а поток этот зависит от уровней
выше. Оптимальность Белади доказана для единой политики на весь бюджет,
а не для цепочки независимо-оптимальных звеньев.

Насколько это существенно — замер на 500 случайных обращениях (12
различных ключей), конфиг `1 LRU / 2 ARC / 1 LIRS / 3 LFU / 2 2Q`,
суммарная ёмкость 9:

| прогон                                  | хитов |
|-----------------------------------------|-------|
| реальная иерархия                       | 305   |
| каскад из 5 идеальных уровней           | 283   |
| **один идеальный кеш ёмкости 9**        | **442** |

Каскад не просто занижен — он *ниже реальной иерархии*, то есть в роли
верхней границы бесполезен. Поэтому эталоном служит один
`TIdealCache` с ёмкостью `SumCapacities(LevelConfigs)`
(см. `MakeIdealConfig()` в `src/main.cpp`).

Проверено: 300 случайных конфигураций (1–4 уровня, ёмкости 1–6, потоки до
200 обращений) под ASan+UBSan — суммарные хиты реальной иерархии не
превысили идеал ни разу.

## Важный нюанс, найденный при тестировании

При стресс-тестировании (300+ случайных конфигураций/потоков, ASan+UBSan)
всё сошлось с ожиданиями с одним интересным исключением: **при ёмкости
уровня, равной 1, у LIRS и 2Q число хитов иногда превышало идеальный
кеш** — что в теории невозможно (Белади доказанно оптимален).

Причина не в арифметической ошибке, а в самой природе этих алгоритмов:
у LIRS и 2Q есть служебные "пробационные" под-области (HIR-резидентная
часть у LIRS, `Am` у 2Q), которые при общей ёмкости 1 вырождаются в 0.
В этом состоянии алгоритм вместо вытеснения существующего резидента
начинает попросту **отказывать новым ключам в приёме**, оставляя старый
резидент нетронутым — то есть ведёт себя как политика *допуска* (admission
policy), а не только *вытеснения* (eviction policy). Классический же
Белади (реализованный здесь) следует стандартной модели вынужденной
подкачки: любой промах обязан внести запрошенный элемент, вытеснив
кого-то. Политика допуска — более широкое пространство стратегий, и в
отдельных последовательностях она способна обыграть классический Белади
именно потому, что Белади такую опцию не рассматривает (похожая идея лежит
в основе admission-политик вроде TinyLFU).

Чтобы сравнение оставалось корректным, ёмкость 1 для LIRS и 2Q явно
обработана отдельным тривиальным путём — однослотовый кеш с обязательной
заменой на промахе, как и подобает кешу ёмкости 1. При ёмкости ≥ 2 подобных
нарушений не возникло ни в одном из 1500 случайных прогонов.

## Про правило "system-specific функции — под Linux"

Задача не потребовала ничего платформенно-зависимого (только чтение файла
и stdin через стандартные потоки C++), поэтому никаких POSIX/Linux-специфичных
вызовов не использовалось — добавлять их искусственно означало бы нарушить
правило "не изобретай сверх необходимого". Если бы в будущем понадобился,
например, `mmap` для больших файлов данных или точные таймеры — их стоит
брать из `<sys/mman.h>` / `<time.h>` (Linux), а не кроссплатформенные обёртки.

## Возможные доработки

- `TIdealCache` при очень большой ёмкости и очень длинном потоке всё ещё
  O(log C) на операцию — для миллиардов обращений можно рассмотреть более
  тонкую структуру, но для учебной/исследовательской симуляции этого с
  большим запасом достаточно (500k обращений при суммарной ёмкости 2000 —
  ~0.6 сек).
- Ключ жёстко типизирован как `long long` (`int`), потому что во всех
  входных данных задачи — целые идентификаторы; сами структуры кешей
  шаблонные и без изменений заработают с любым `Key` с `std::hash`.
